### 2-2. 렌더링 아키텍처 (VS6)

```
MTopView (게임 화면 로직)
  └─ CSpriteSurface  (SpriteLib) ── CDirectDrawSurface 상속
       └─ CDirectDrawSurface::Blt/Lock/Unlock/FillSurface
            └─ LPDIRECTDRAWSURFACE7 (DirectDraw7 Surface, 하드웨어 Blt/컬러키)
                 └─ CDirectDraw::Flip() → Primary/Back Surface 교체

CDirect3D (D3DLib, CDirectDraw 상속) — 텍스처 관리용 보조 계층
  └─ LPDIRECT3DDEVICE7 / LPDIRECT3D7
```

- 실질적인 게임 화면(타일/캐릭터/이펙트)은 **DirectDraw 2D Blt** 중심으로 그려진다.
  `CDirect3D`는 텍스처 서페이스 관리(`DDSCAPS2_TEXTUREMANAGE`) 용도로 보조적으로 존재.
- `CDirectDraw`는 런타임에 하드웨어 픽셀 포맷(565/555), MMX 지원, 감마 컨트롤 지원 여부를
  `Check565()`/`CheckMMX()`/`CheckGammaControl()`로 **직접 감지**하여 분기 처리한다.
- `CDirectDrawSurface`는 `SYSTEMMEMORY`/`VIDEOMEMORY` Surface 캐퍼빌리티를 선택적으로 사용
  (Alpha Blending은 SYSTEMMEMORY 권장 — 주석에 명시).

## 3. VS2019(SDL2) 그래픽 스택 상세

### 3-1. 사용 라이브러리

- **SDL2** (필수) — 윈도우/렌더러/서페이스/이벤트
- **SDL2_image** (필수) — 이미지 로딩 보조
- **SDL2_ttf**(+freetype2 내장) — 텍스트 렌더링, `GDI_Text` 대체 예정
- **SDL2_mixer** — 효과음/배경음악(사운드 계열, 참고용)
- **libjpeg / libjpeg-turbo**(vcpkg, 선택) — JPEG 로딩

### 3-2. SpriteLib SDL2 백엔드 구조

`Client/SpriteLib/SPRITELIB_BACKEND_README.md`, `SpriteLibBackendSDL.h` 기준:

```
Game Code (MTopView, MCreature 등) — 원본 CSprite* API 그대로 사용
   ↓
SpriteLib Adapter Layer
   CSpriteSurface_Adapter.cpp (API 서명 유지)
   CSprite_SDL.cpp            (백엔드 핸들 관리)
   ↓
SpriteLibBackend.h (C 인터페이스)
   spritectl_create_surface() / spritectl_create_sprite() / spritectl_blt_sprite() ...
   ↓
SpriteLibBackendSDL.cpp (SDL2 구현)
```

- `spritectl_surface_s { SDL_Surface* surface; SDL_Texture* texture; SDL_Renderer* renderer; ... }`
- `spritectl_sprite_s { uint16_t* pixels(565/555); uint16_t** scanline_rle; uint32_t* rgba_pixels(SDL 렌더 캐시); ... }`
- 스프라이트 팩은 **지연 로딩(Lazy Loading)** 지원 — 파일 오프셋만 미리 읽고 픽셀은 첫 접근 시 로드
  (VS6에는 없던 최적화, `참고자료/분석관련/03-1. 렌더링 시스템 상세.md` 7절 참조)

### 3-3. `CSpriteSurface` 클래스 계층 단절

`Client/SpriteLib/CSpriteSurface.h`는 매크로 조합에 따라 **두 가지 클래스 정의**를 갖는다.

```cpp
#ifdef SPRITESURFACE_STANDALONE
  #ifdef SPRITELIB_BACKEND_SDL
    class CSpriteSurface { ... };                    // ← 현재 빌드가 사용하는 버전. 상속 없음(독립 클래스)
  #else
    class CSpriteSurface : public CDirectDrawSurface { ... };  // 레거시(Windows 네이티브) 버전, 미사용
  #endif
#endif
```

- 루트 `CMakeLists.txt`가 `USE_SDL_BACKEND`를 모든 플랫폼에서 강제 `ON`으로 고정하므로,
  실제 빌드에서는 **상속 없는 SDL 독립 클래스**만 컴파일된다.
- 즉 VS6에서 "`CSpriteSurface` is-a `CDirectDrawSurface`" 였던 관계가
  VS2019(SDL2)에서는 완전히 끊어졌고, `CDirectDrawSurface`는 이름만 남은 클래스다.

### 3-4. `CDirectDraw`/`CDirectDrawSurface`의 현재 실체 — **레거시 스텁**

`Client/DXLib/CDirectDrawSurface.cpp` 첫머리 주석:

```
// SDL2 Implementation (Cross-platform)
// Windows DirectDraw implementation removed - using SDL2 on all platforms
// NOTE: This class is deprecated. Use SDL_Surface directly instead.
```

- `CDirectDraw.cpp` / `CDirectDrawSurface.cpp`는 `Client/DXLib/CMakeLists.txt`에서
  **항상 컴파일 대상에 포함**되지만, 내부 구현은 DirectDraw API 호출이 전부 제거된
  빈 스텁(멤버 초기화 정도)이다. 실질적인 렌더링은 위 3-2의 SpriteLib SDL 백엔드가 전담한다.
- `Client/D3DLib` 폴더는 **VS2019 트리에 존재하지 않는다** (완전 삭제).
  `CDirect3D::GetDevice()` 관련 코드는 `참고자료/분석관련/03-1. 렌더링 시스템 상세.md` 15절 기준
  `nullptr` 반환 스텁으로만 남아 있고, `CD3DTextureEffect`는 `#ifdef PLATFORM_WINDOWS`로만
  컴파일되는 사실상 비활성 코드다.
- `Client/DXLib/CMakeLists.txt:79-82`에 명시적 경고:
  `"Windows DirectX backend not yet implemented. Please use USE_SDL_BACKEND=ON"`
  → VS2019 빌드에서도 DirectX 네이티브 백엔드는 선택지가 아니며 SDL2가 유일한 경로.

## 5. 픽셀 포맷/이펙트 로직 비교

- 저장/메모리 픽셀 포맷(RGB565, RGB555, RGBA4444, A1RGB555)은 **로직 그대로 이식**됨.
  VS6는 `CDirectDraw::Convert555to565`류 정적 함수로 처리하던 것을, VS2019는
  `SpriteLibBackendSDL.h`의 `spritectl_565_to_rgb()` 등 별도 인라인 함수로 재구현.
- VS2019 SDL 백엔드는 **RGBA32 캐시**(`rgba_pixels`)를 추가로 두어 SDL 텍스처/렌더러에
  바로 먹일 수 있게 한다 — VS6에는 없던 개념(DirectDraw는 565/555 서페이스에 직접 Blt).
- 색상 교체(`ColorSet`), 이펙트 함수 테이블(`EFFECT_DARKER` 등 14종), RLE 압축 스프라이트
  포맷은 VS6/VS2019 동일 구조 유지 (`참고자료/분석관련/03-1. 렌더링 시스템 상세.md` 5~7절).

## 6. 확인이 필요한 항목 (미해결)

1. **감마 램프 제어** — VS6의 `SetGammaRamp`/`SetAddGammaRamp` 계열이 VS2019에서
   실제로 대체되었는지, 아니면 완전히 드롭되었는지 소스 재확인 필요.
2. **런타임 포맷 감지 vs 빌드 타임 고정** — VS6은 `Check565()`로 하드웨어에 맞춰 565/555를
   런타임 선택했지만, VS2019는 이 로직이 보이지 않음(빌드 매크로로 고정된 것으로 추정).
3. **`lib/` 루트의 VS6 전용 라이브러리**(`GL.lib`, `IFC22.lib`, `PS.lib`, `Timer.lib`, `rbt.lib`) —
   이름만으로는 용도 불명. 그래픽 관련 여부(특히 `GL.lib`가 OpenGL인지) 별도 확인 필요.
   VS2019 쪽에는 대응하는 `lib/` 폴더 자체가 없음.
4. ~~`CTexturePartManager` 계열이 Direct3D 없이 어떻게 동작하는지~~ — **확인 완료.**
   `Client/CTexturePartManager.h`는 더 이상 `CDirect3D`/`LPDIRECT3D*`를 전혀 참조하지 않고
   `SpriteLib/CSpriteSurface.h`(SDL 백엔드)만 사용하도록 이미 재작성되어 있음
   (`class CTexturePartManager : public CPartManager<WORD, WORD, CSpriteSurface*>`). 데드코드가
   아니라 D3D 의존을 완전히 걷어내고 SDL 서페이스 기반으로 재구성된 상태 — 7절 참고.
5. **`CDirectDraw`/`CDirectDrawSurface` 스텁 클래스의 실제 참조 여부** — 완전히 죽은 코드인지,
   일부 레거시 경로(예: `SPRITELIB_BACKEND_SDL` 미정의 빌드)에서만 쓰이는지 확인 필요.

## 7. Direct3D 삭제에 대한 대안 — 3D/텍스처 가속이 필요해질 경우의 라이브러리 선택지

> 3절에서 확인했듯 VS2019에서는 `D3DLib` 폴더 자체가 삭제되어 Direct3D 계열이 전혀 없다.
> "무엇으로 되살려야 하는가"를 판단하려면 먼저 **VS6에서 Direct3D가 실제로 어떤 역할이었는지**를
> 봐야 한다.

### 7-1. VS6에서 Direct3D의 실제 역할 — "3D 렌더링"이 아니라 "텍스처 가속"

- `Client/D3DLib/CDirect3D.h` 주석(`Texture가 재사용될 Surface에 추가되면 좋은 flag`,
  `DDSCAPS2_TEXTUREMANAGE`)과 멤버 구성(`GetTextureSize()`, `m_TextureWidthMax/HeightMax`,
  `m_PixelFormat4444/1555`)을 보면, `CDirect3D`는 폴리곤/모델을 그리는 진짜 3D 렌더러가
  아니라 **DirectDraw Surface를 하드웨어 텍스처 메모리에 올려 Blt를 가속하기 위한
  텍스처 관리 계층**이다. 실제 화면(타일/캐릭터/이펙트)은 2절에서 정리한 대로 여전히
  `CDirectDraw`/`CDirectDrawSurface`의 2D Blt 파이프라인이 그린다.
- `CTexturePartManager`/`CSpriteTexturePartManager`가 이 텍스처 관리 계층을 사용하는
  상위 코드였고, VS2019에서는 이미 `CDirect3D` 참조를 걷어내고 `CSpriteSurface`(SDL)를
  직접 쓰도록 재작성되어 있다 (6절 4번 항목).
- 즉 VS6도 "3D 그래픽스"를 쓴 게 아니라 **2D Blt를 GPU 텍스처로 가속**했을 뿐이다.
  → VS2019가 채울 자리는 "3D API"가 아니라 "2D 텍스처/블릿 가속"이다.

### 7-2. VS2019 현재 상태 — 이미 SDL2만으로 그 역할을 대체하고 있음 (그러나 절반만 사용 중)

`Client/SDLMain.cpp`와 `Client/SpriteLib/SpriteLibBackendSDL.cpp`를 확인한 결과:

- 메인 윈도우는 `SDL_CreateRenderer(window, -1, SDL_RENDERER_ACCELERATED)`로 **GPU 가속
  렌더러**를 이미 쓰고 있다(`Client/SDLMain.cpp:153`).
- 하지만 개별 스프라이트/서페이스(`spritectl_surface_s`) 단위로는 `renderer` 필드가
  항상 `NULL`로 세팅되어 있다(`SpriteLibBackendSDL.cpp:158`) — 즉 **스프라이트 블릿 자체는
  여전히 CPU 측 `SDL_Surface` 소프트웨어 Blt(RLE 기반)로 처리**되고, GPU 가속 렌더러는
  프레임 전체를 합성한 최종 화면 한 장을 `spritectl_present_surface()`로 텍스처 업로드해
  `SDL_RenderPresent()`로 출력하는 데에만 쓰인다(`SDLMain.cpp:503-517`).
- 결과적으로 지금 구조는 "**프레임당 텍스처 업로드 1회 + GPU Present**" 방식으로, VS6의
  DirectDraw `Flip()`(백버퍼→화면 전환)과 정확히 같은 역할을 SDL2 하나로 이미 대체하고
  있다. 800×600 해상도의 2D 아이소메트릭 게임에서는 이 정도로 충분히 성능이 나온다.
- 반면 VS6의 `CDirect3D`가 하던 "**개별 스프라이트를 하드웨어 텍스처로 상주시켜 Blt마다
  가속**"하는 역할은 VS2019에 없다 — 다만 `spritectl_surface_s`에 `texture`/`renderer`
  필드가 이미 준비되어 있고 `SPRITELIB_BACKEND_SDL`의 texture 슬롯이 "선택적(GPU 렌더링용)"
  으로 주석되어 있으므로, **필요해지면 별도 3D 라이브러리 없이 SDL2 자체 기능(`SDL_CreateTexture`
  + `SDL_RenderCopy`)만으로 채울 수 있는 빈 슬롯**이다.

### 7-3. 결론 — 지금 당장은 3D 라이브러리 도입 불필요, 필요해질 때의 선택지

| 상황 | 권장 | 이유 |
|---|---|---|
| **현재 상태 유지 (2D 아이소메트릭, 실측 성능 문제 없음)** | **아무것도 도입하지 않음** | 게임 성격상 실제 3D 지오메트리를 그린 적이 없고, VS6의 D3D도 텍스처 가속용이었을 뿐. 위 7-2의 "프레임당 1회 업로드" 구조로 이미 충분 |
| **스프라이트 블릿 성능이 실제로 병목이 되는 경우** | **SDL2 자체 GPU 경로 확장 (권장, 별도 라이브러리 불필요)** | `spritectl_surface_s`의 미사용 `texture`/`renderer` 필드를 채워, 자주 그려지는 스프라이트 팩을 `SDL_CreateTexture`로 캐싱 후 `SDL_RenderCopy`로 Blt — VS6 `CDirect3D`의 "텍스처 상주" 역할과 정확히 대응. 이미 프로젝트가 링크 중인 SDL2만으로 해결, 빌드 시스템 변경 없음 |
| **신규 3D 요소가 실제로 필요해지는 경우 (셰이더 기반 이펙트, 3D 모델 등)** | **SDL2 + OpenGL 3.3 Core Context** (`SDL_GL_CreateContext`) | SDL2가 이미 의존성에 있으므로 추가 라이브러리 없이 최소 마찰로 크로스플랫폼(Win/macOS/Linux) 3D 확보. macOS는 OpenGL 4.1 상한 + deprecated 경고가 있지만 여전히 동작 |
| **여러 네이티브 그래픽 API(D3D11/12, Metal, Vulkan)를 백엔드별로 최적화해야 하는 대규모 확장** | **bgfx 또는 Diligent Engine** 검토 | 플랫폼별 최상의 API(Windows=D3D, macOS=Metal, Linux=Vulkan/OpenGL)로 자동 라우팅되는 크로스플랫폼 렌더 추상화. 단, 자체 빌드 도구(bgfx의 GENie/bx/bimg, 셰이더 컴파일 파이프라인)를 CMake 빌드에 통합해야 해서 비용이 크므로 실제 3D 콘텐츠 요구가 확정된 뒤에만 검토 |
| **(비권장) Direct3D 자체 재도입** | 권장하지 않음 | VS6이 쓰던 Direct3D 7은 이미 수명이 끝난 API고, Windows 전용이라 이 프로젝트의 크로스플랫폼(SDL2 기반 Win/macOS/Linux) 목표와 정면으로 상충함. D3D11/12로 새로 짜더라도 Windows에서만 쓸 별도 백엔드 유지 비용이 추가로 발생 |

**요약**: VS6의 Direct3D는 실질적으로 "텍스처 가속 Blt" 용도였고, VS2019는 이미 SDL2의
GPU 가속 렌더러로 그 자리(프레임 Present)를 대체했다. 스프라이트 단위 텍스처 캐싱까지
넣고 싶다면 새 라이브러리 없이 SDL2의 `SDL_Texture`/`SDL_Renderer`를 마저 활용하면 되고,
진짜 3D 콘텐츠가 필요해지는 시점에만 SDL2+OpenGL → (필요시) bgfx/Diligent 순으로
검토하는 것이 프로젝트의 크로스플랫폼 방향성과 맞는다.
