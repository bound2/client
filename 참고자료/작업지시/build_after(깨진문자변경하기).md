## 1. 발견한 문제

`Client\GameMain.cpp`을 열어보면 한글/중국어가 있어야 할 자리에 `Çï±âÀå`,
`ÒÔÏÂÕâ¶Î¼ì²â·Ç·¨½ø³Ì` 같은 알 수 없는 문자(모지바케)가 대량으로 섞여 있었음.

### 원인
- 원본(`client-master_vs6`)의 소스 파일 자체가 **CP949(한글)와 GBK(중국어)가 한
  파일 안에 섞여 있는 레거시 인코딩**이었음. 이 프로젝트는 원래 한국 개발사
  (Softon)가 CP949로 작성했지만, 이후 중국 사설서버 쪽에서 안티치트/핵차단
  기능(`CheckInvalidProcess()` 주변)을 GBK로 추가한 것으로 보임.
- 이 CP949/GBK 혼용 원본 바이트가 어느 시점에 **각 바이트를 Latin-1(ISO-8859-1)로
  1:1 매핑해서 UTF-8로 재저장**하는 잘못된 변환을 거쳤음 (전형적인
  "Latin-1 모지바케"). 그 결과 `Ç`, `¬`, `½` 같은 라틴 확장 문자 뭉치로 보이게 됨.
  UTF-8 자체는 유효해서 (디코딩 에러는 안 남) 컴파일은 되지만 텍스트가 전부
  의미를 잃은 상태.
- 이 모지바케 변환은 **역산 가능한 결정론적 변환**이라, 현재 dk_client 파일의
  깨진 문자를 vs6 원본과 대조하지 않고도, 문자 하나하나를 다시 Latin-1로
  바이트화(`encode('latin-1')`) → CP949로 우선 디코딩 → 결과에 한자(CJK
  Unified Ideographs)가 섞여 나오면 GBK로 재시도, 하는 방식으로 그대로 복원
  가능했음.

### `GameMain.cpp`에서 실제로 한 작업
1. **`g_strBadProcessList` 배열** (중국 게임핵 프로그램 이름 20개) - 사용자가
   이전에 CP949로 잘못 복원해서 "긴醵", "쏜踏舅" 같은 한글+한자가 섞인
   무의미한 문자열이 되어 있었음. vs6 원본 바이트를 GBK로 다시 디코딩해서
   `变速`(변속), `加速`(가속), `金山游侠`(진산유샤 - 중국 게임핵 툴 이름) 등
   실제 중국어 텍스트로 복원. 이 배열은 실행 중인 프로세스의 창 제목과
   문자열 비교를 하는 안티치트 로직이라, 실제 핵 프로그램의 (중국어) 창
   제목과 일치해야 정상 동작 - 한글로 바꾸면 안 됨.
2. **파일 전체 모지바케 스캔/복원** - 코드포인트 `U+0080~U+00FF` 범위 문자가
   포함된 줄 436개를 자동 탐지, 줄 단위로 CP949 우선 → 한자 섞이면 GBK
   재시도 방식으로 전부 복원. 자동판별로 안 잡힌 1곳(`yckou` 주석, 순수
   한글로도 유효하게 디코딩되어버려 자동 휴리스틱을 통과 못함)은 GBK로
   수동 수정.
   - 436줄 전부 육안 검토 완료 (한국인 개발자가 남긴 정상적인 개발 주석들:
     "화면에 debug메세지를 출력할까?", "PC가 제대로 생성되었나?" 등, 그리고
     안티치트 함수 주변 중국어 주석/메시지박스 텍스트 11곳 정도).
   - `difflib`로 정확히 이 436줄만 바뀌고 나머지 5433줄은 원본과 100% 동일함을
     확인 (코드 로직은 전혀 건드리지 않음).
   - 파일 맨 앞에 UTF-8 BOM 추가 (BOM 없으면 MSVC가 CP949로 오인식해서
     `error C2001`류의 허위 구문 오류가 남 - `VS_UI_GameCommon.cpp` 등에서
     이미 겪었던 것과 동일한 문제, `참고자료\커밋로그\2026-08-19_VS_UI_GameCommon_UTF8_BOM_추가.md`
     참고).
3. `cmake --build build/vs2019 --config Debug --target DarkEden`으로 재빌드,
   컴파일 오류 0건 확인.

## 2. 다음 세션에서 할 일 - 프로젝트 전체 스캔/복원

`GameMain.cpp` 하나만 이 문제가 있었을 가능성은 낮음. 같은 시기에 같이
변환됐을 다른 `.cpp`/`.h` 파일들도 같은 모지바케를 가지고 있을 것으로 추정.

### 진행 방법 (이번에 검증된 절차 그대로)
1. `dk_client`의 각 소스 파일에서 코드포인트 `U+0080~U+00FF` 범위 문자가
   포함된 줄을 스캔 (이 범위에 있으면 100% 모지바케 - 정상적으로 이미
   복원된 한글/한자는 이 범위 밖(`U+AC00~`, `U+4E00~`)이라 안 걸림, 오탐 없음).
2. 걸린 줄마다: `latin-1`로 재인코딩 → 원래 바이트 복원 → CP949로 우선
   디코딩 → 결과에 CJK 통합 한자가 섞여 있으면 GBK로 재시도.
3. 복원 결과를 diff/report로 남겨서 **육안으로 전수 검토** (자동 휴리스틱이
   놓치는 케이스가 있었음 - `GameMain.cpp`의 `yckou` 주석처럼 순수 한글로도
   "유효하게" 디코딩돼버리는 경우는 사람이 봐야 이상함을 알아챌 수 있음).
   필요하면 `client-master_vs6`의 대응 파일과 나란히 놓고 대조.
4. 변경 줄 수가 원본과 정확히 일치하는지, 나머지 줄은 100% 동일한지
   `difflib`로 검증 후 적용.
5. UTF-8 BOM이 없는 파일은 같이 추가 (MSVC의 CP949 오인식으로 인한 허위
   컴파일 오류 방지).
6. 파일 하나 고칠 때마다 해당 타겟만 재빌드해서 컴파일 오류 없는지 확인.

### 주의할 점
- CP949로 디코딩이 "성공"한다고 해서 항상 맞는 건 아님 (GBK 바이트도 우연히
  유효한 CP949로 디코딩되는 경우가 있음 - 이번 `g_strBadProcessList`,
  `yckou` 주석이 그 예). 결과에 한자가 섞이는지, 문맥상 말이 되는지 반드시
  확인.
- 안티치트/핵차단 관련 코드(`CheckInvalidProcess()` 류)나 중국 서버 관련
  주석은 GBK일 가능성이 높고, 그 외 일반 개발 주석은 CP949(한글)일
  가능성이 높음 - 하지만 예외가 있을 수 있으니 자동화만 믿지 말 것.
