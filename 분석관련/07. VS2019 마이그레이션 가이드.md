# 7. VS2019 마이그레이션 가이드

---

## 결론 요약

| 항목 | 상태 |
|------|------|
| 빌드 시스템 호환성 | ✅ CMake → VS2019 솔루션 생성 가능 |
| C++ 표준 | ✅ C++11 — VS2019 완전 지원 |
| 플랫폼 추상화 | ✅ `basic/Platform.h` 설계가 Windows 우선 |
| WinMain 진입점 | ❌ **미해결 — 링크 실패 가능성 높음 (4-5 참조)** |
| DirectX 백엔드 | ❌ 미구현 (SDL 백엔드만 존재) |
| SDL2 의존성 | ⚠️ Windows에서 수동 설치 필요 |
| iconv 의존성 | ⚠️ Windows용 별도 라이브러리 필요 |
| Sanitizer (ASAN 등) | ❌ MSVC에서 미지원 (GCC/Clang 전용) |

**빌드 자체는 가능하나, SDL2 + iconv 의존성 설치 외에 WinMain 진입점 충돌(4-5)을 먼저 해결해야 한다. 이게 이 문서에서 가장 확실한 실제 블로커다.**

## 1. 현재 빌드 시스템 구조

```
CMakeLists.txt (루트)
├── cmake_minimum_required(VERSION 3.10)
├── set(CMAKE_CXX_STANDARD 11)
├── set(USE_SDL_BACKEND ON ... FORCE)   ← 모든 플랫폼에서 강제 ON
├── find_package(SDL2 REQUIRED)
├── find_package(SDL2_image REQUIRED)
├── find_package(SDL2_ttf REQUIRED)
├── find_package(JPEG QUIET)
└── target_link_libraries(DarkEden ... iconv)
```

- `.sln` 파일 없음 — **CMake로 VS 솔루션을 생성해야 함**
- VS2019 제너레이터: `"Visual Studio 16 2019"`

## 3. CMake 빌드 명령

### 3-1. VS2019 솔루션 생성

```powershell
cd C:\Users\USER\Desktop\Github_clone\dk_client

cmake -S . -B build\vs2019 ^
  -G "Visual Studio 16 2019" ^
  -A x64 ^
  -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake ^
  -DUSE_SDL_BACKEND=ON ^
  -DCMAKE_BUILD_TYPE=Debug
```

- `-G "Visual Studio 16 2019"` : VS2019 솔루션/프로젝트 생성
- `-A x64` : 64비트 타겟
- `-DCMAKE_TOOLCHAIN_FILE` : vcpkg 패키지 자동 검색
- `-DUSE_SDL_BACKEND=ON` : 명시적 지정 (루트에서 이미 FORCE이나 명시 권장)

### 3-2. 빌드

```powershell
cmake --build build\vs2019 --config Debug
```

또는 `build\vs2019\DarkEdenClient.sln`을 VS2019에서 열어 빌드.

## 4. 예상 이슈 및 해결 방법

### 4-1. Sanitizer 옵션 (MSVC 미지원)

현재 CMakeLists.txt의 Sanitizer 설정이 GCC/Clang 전용:

```cmake
# CMakeLists.txt 라인 28
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    ...  # ASAN/TSAN/UBSAN 플래그 추가
endif()
```

MSVC는 조건에 해당하지 않으므로 **자동으로 제외**됨 → 별도 조치 불필요.

MSVC에서 유사한 메모리 검사를 원하면:
```powershell
cmake ... -DCMAKE_CXX_FLAGS="/fsanitize=address"
```
(VS2019 16.9+ 부터 `/fsanitize=address` 지원)

### 4-2. iconv 링크 오류

`libiconv`가 없을 경우 링크 실패. 해결 방법:

**방법 A**: vcpkg로 설치 (권장)
```powershell
C:\vcpkg\vcpkg install libiconv:x64-windows
```

**방법 B**: CMakeLists.txt 조건부 처리 (WIN32 제외)
```cmake
# CMakeLists.txt의 iconv 링크 부분 수정
if(NOT EMSCRIPTEN AND NOT WIN32)
    target_link_libraries(DarkEden PRIVATE iconv)
endif()
```
Windows에서는 `MultiByteToWideChar` / `WideCharToMultiByte` (Win32 API)로 대체 가능하므로 iconv가 실제로 필요 없을 수 있음.

### 4-3. macOS 전용 하드코딩 경로

루트 CMakeLists.txt 상단의 Homebrew 경로:

```cmake
# 라인 4-8
if(EXISTS "/opt/homebrew/include/SDL2")
    ...
elseif(EXISTS "/usr/local/include/SDL2")
    ...
endif()
```

Windows에서는 경로가 존재하지 않으므로 분기에 진입하지 않음 → **무해, 별도 조치 불필요**.

### 4-4. `#pragma comment(lib, ...)` — winmm / th32

```cpp
// Client/CAvi.cpp:13
#pragma comment(lib, "winmm.lib")
// Client/CGameUpdate.cpp:111
#pragma comment(lib, "th32")
```

`winmm.lib`은 Windows SDK에 포함 → 자동 링크. 문제없음.

`th32.lib`은 ~~프로세스 열거용 `toolhelp32.lib` 일부~~ **실제로는 존재하지 않는 라이브러리**다. Win95~NT 시절 유물이며, ToolHelp32 계열 함수(`CreateToolhelp32Snapshot` 등)는 현대 Windows SDK에서 이미 `kernel32.lib`에 포함되어 자동 링크된다.

~~필요 시 CMakeLists.txt에 추가: `target_link_libraries(DarkEden PRIVATE ... toolhelp32)`~~ → **이것도 존재하지 않는 이름이라 동일하게 실패한다.**

**올바른 해결**: `Client/CGameUpdate.cpp:111`의 `#pragma comment(lib, "th32")` 줄을 삭제. VS2019 빌드 시 `LNK1104: cannot open file 'th32.lib'`가 나면 여기가 원인이다.

### 4-5. WinMain 진입점 — ⚠️ 실제 블로커, 재검토 결과 문제 확인됨

```cpp
// VS_UI/WinMain.cpp:3186
int WINAPI WinMain(HINSTANCE hInst, HINSTANCE hPrevInst, LPSTR lpszArgs, int nWinMode)
```

~~단, CMakeLists.txt 라인 529 `NOT WIN32` 블록에서 제외 목록을 확인 → WIN32에서는 `WinLib/CWinMain.cpp`가 포함됨. 내용 확인 필요.~~

**정정**: `Client/WinLib/CWinMain.cpp`는 존재하지 않는다. `Client/WinLib/WinLib.h:5`에 `// CWinMain removed - using SDL2 on all platforms`라고 명시되어 있어 이미 삭제된 상태다. `CMakeLists.txt:556`의 `EXCLUDE REGEX "WinLib/CWinMain\\.cpp"` 필터는 대상 파일이 없는 죽은 코드다. 즉 실제 진입점은 처음부터 `VS_UI/WinMain.cpp` 하나뿐이며, 여기서 확인할 "내용"은 없다.

**대신 실제로 확인해야 할 문제 두 가지**:

1. **`add_executable`에 `WIN32` 키워드 없음** (`CMakeLists.txt:562`)
   ```cmake
   add_executable(DarkEden ${CLIENT_MAIN_SOURCES})
   ```
   MSVC는 기본적으로 콘솔 서브시스템(`/SUBSYSTEM:CONSOLE`)으로 링크하며 `main`/`wmain` 진입점을 찾는다. 소스에는 `main`이 없고 `WinMain`만 있으므로 `LNK2019: unresolved external symbol main` 이 날 수 있다.

2. **`SDL2::SDL2main`과 수동 `WinMain`의 충돌 가능성** (`CMakeLists.txt:286, 578`)
   `VS_UI`와 `DarkEden` 둘 다 `SDL2::SDL2main`을 링크한다. Windows에서 `SDL2main.lib`은 자체 `WinMain`을 제공해 `SDL_main()`으로 포워딩하는 방식(코드에서 `#define main SDL_main` 관례 사용을 전제)인데, `VS_UI/WinMain.cpp`는 그 관례를 따르지 않고 **직접 `WINAPI WinMain`을 정의**한다. 두 심볼이 최종 링크에서 충돌하면 `LNK2005: WinMain already defined`가 날 수 있다.
   macOS 빌드가 지금까지 멀쩡했던 건 SDL2main이 Unix 계열에서는 사실상 no-op이라 이 문제가 드러나지 않았기 때문으로 보인다.

   **제안하는 수정 방향** (검증 필요, 아직 CMakeLists.txt에 미적용):
   ```cmake
   if(WIN32)
       add_executable(DarkEden WIN32 ${CLIENT_MAIN_SOURCES})
   else()
       add_executable(DarkEden ${CLIENT_MAIN_SOURCES})
   endif()
   ...
   target_link_libraries(DarkEden PRIVATE SDL2::SDL2)
   if(NOT WIN32)
       target_link_libraries(DarkEden PRIVATE SDL2::SDL2main)
   endif()
   ```
   (`VS_UI` 쪽 `SDL2::SDL2main` 링크도 동일하게 WIN32에서 제외 검토 필요)

### 4-6. Windows 전용 Imm (Immersion) 라이브러리

```cmake
# CMakeLists.txt 라인 612-616
if(WIN32)
    target_include_directories(DarkEden PRIVATE
        ${CMAKE_CURRENT_SOURCE_DIR}/VS_UI/src/Imm
    )
endif()
```

WIN32에서는 Imm 헤더가 자동 포함됨. 이 헤더들은 `__declspec` 사용 — MSVC에서 정상 동작.

### 4-7. PLATFORM_WINDOWS 미정의 문제

현재 CMakeLists.txt가 WIN32에서 `PLATFORM_WINDOWS`를 `add_definitions`로 정의하지 않음.
`basic/Platform.h`는 컴파일러 내장 `_WIN32` 매크로로 플랫폼 감지하므로 **일반적으로 문제없음**.
만약 플랫폼 관련 컴파일 오류 발생 시:
```cmake
if(WIN32)
    target_compile_definitions(DarkEden PRIVATE PLATFORM_WINDOWS)
endif()
```
